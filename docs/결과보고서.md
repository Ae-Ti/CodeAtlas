## 1. 프로젝트 개요

| 항목 | 내용 |

### 1.1 개발 목적

> 논문 속 핵심 설명과 공개 GitHub 구현 코드를 연결하여 연구자와 개발자가 알고리즘
> 구현 위치를 빠르게 찾고 재사용할 수 있는 오픈소스 개발 지원 도구를 개발한다.

### 1.2 프로젝트 소개

CodeAtlas 는 arXiv 논문과 그에 대응하는 GitHub 오픈소스 구현체를 직접 선별·수집하고,
논문 단락과 코드 블록을 pgvector 기반 유사도 검색으로 매핑하는 웹 플랫폼입니다.
MCP 에이전트가 논문 검색·코드 탐색·구현 위치 확인을 수행하며, 사용자는 코드
하이라이터(Monaco)와 GitHub 원문 링크로 근거를 끝까지 검증할 수 있습니다.

이 문제를 자동으로 풀어주던 **Papers with Code 는 2025년 7월 서비스가 종료**됐습니다.
남은 서비스들은 "어떤 논문에 코드가 있는가"까지만 다루며, **논문 안의 어느 단락이
코드의 어느 함수에 해당하는가**는 다루지 않습니다. CodeAtlas 는 그 마지막 한 칸을
채웁니다.

### 1.3 기대 효과

논문 이해와 구현 탐색에 드는 시간을 줄이고, 연구 결과의 재현성과 오픈소스 코드
재사용성을 높입니다. MCP 기반 도구 호출, pgvector 검색, NL2SQL 질의 기능을
오픈소스로 제공하여 다른 연구 문서·기술 문서·코드베이스 분석 도구로 확장 가능한
개발자 생태계 인프라를 지향합니다.

### 2.2 구축 방식 — 수동 큐레이션

논문 1편당 사람이 읽고 단락을 나눈 뒤, 각 단락에 대응하는 코드 위치를 지정했습니다.
자동 수집을 쓰지 않은 이유는 **오탐 한 건의 비용이 특히 크기** 때문입니다 — "이 단락은
이 함수입니다"라고 단정해 놓고 틀리면 사용자는 검증하려 저장소를 직접 뒤지게 되고,
그 순간 제품이 존재할 이유가 없어집니다.

파이프라인은 다음과 같습니다. 각 단계 산출물이 저장소에 남아 있어 재현할 수 있습니다.

```
큐레이터 노트(마크다운)
  └─▶ scripts/note2ingest/    노트 파싱 · 코드 위치 역매칭 · 쪽 번호 대조
        └─▶ database/ingest/*_ingest.json      ← 커밋됨
              └─▶ scripts/ingest.py            스키마 검증 후 적재
                    └─▶ PostgreSQL 17 + pgvector
```

**코드 본문은 노트가 아니라 저장소 원문에서 가져옵니다.** 초기에는 노트에 적힌 코드를
그대로 넣었는데, 검수 과정에서 14개 블록 중 13개가 저장소와 바이트 단위로 일치하지
않는다는 것을 발견했습니다(노트를 쓰며 줄여 적은 것). 지정된 커밋의 해당 줄 범위를
직접 잘라 오도록 바꿨습니다.

### 2.4 매핑하지 않은 61건 — 억지로 채우지 않았습니다

코드를 붙이지 않은 단락 61건을 **하나씩 판정**했습니다. 판정과 근거는
`scripts/note2ingest/tally_unmapped.py` 에 단락 단위로 적혀 있어 재현·검증할 수 있습니다.

| 사유 | 건수 | 뜻 |
|---|---:|---|
| **A. 저장소가 그 구현을 배포하지 않음** | **24 (39.3%)** | 논문은 구현 요소로 서술했으나 인용 저장소에 그 코드가 없음 |
| **B. 코드로 표현되는 대상이 아님** | **32 (52.5%)** | 실험 결과·수치, Figure/Table, Reference, 타 시스템 설명, 하드웨어·일정, 결론 |
| C. 저장소엔 있으나 인덱싱 범위 밖 | 2 (3.3%) | 코드는 존재하지만 이번 큐레이션에서 블록으로 뽑지 않음 |
| D. 대응이 느슨해 정답셋에 넣지 않음 | 3 (4.9%) | 후보 심볼은 있으나 "이 단락의 구현"이라 단정하기 어려워 비워 둠 |

**A 가 39.3% 로 예상보다 큽니다.** 원인은 공개된 구현이 논문의 일부만 담기 때문입니다.

| 저장소 | 배포 범위 | 그래서 못 붙은 것 |
|---|---|---|
| `meta-llama/llama3` | 추론 코드 3파일 (`generation`·`model`·`tokenizer`) | RLHF·DPO·Reward Modeling·SFT |
| `facebookresearch/segment-anything` | 인코더·디코더·predictor | Loss Function·SA-1B Dataset·Data Engine |
| `KaimingHe/deep-residual-networks` | **ResNet-101 `deploy` prototxt 한 개** | CIFAR 구조·학습 설정·detection 확장 전부 (15건) |

**이 판단은 논문만 읽어서는 나오지 않습니다.** 논문은 학습 절차와 detection 확장에 절을
배정해 상세히 서술하지만, 저자가 공개한 것은 추론 정의뿐입니다. 저장소 인벤토리를 봐야
알 수 있는 구분이고, 자동 분류 실험(확장기능 §5.1)이 이 지점에서 실패한 이유이기도 합니다.

C·D 5건은 데이터의 한계가 아니라 **우리 쪽에서 더 할 수 있었던 부분**입니다.
darknet 의 `examples/demo.c`(webcam)처럼 저장소에 있는데 뽑지 않은 것이 2건,
하이퍼파라미터 표처럼 대응이 느슨해 비워 둔 것이 3건입니다.

```bash
python3 scripts/note2ingest/tally_unmapped.py --list    # 61건 전체를 판정과 함께
```

### 2.5 검증 방법

수치를 만든 뒤가 아니라 **만드는 과정에서** 검증이 걸리도록 했습니다.

| 검증 | 방법 | 잡은 것 |
|---|---|---|
| 스키마 | `ingest.py --dry-run` | 승인 스텁의 빈 초록·저자가 기존 값을 NULL 로 덮어쓸 뻔한 것 |
| 코드 원문 일치 | 저장소 커밋에서 직접 슬라이스 후 대조 | 노트 코드 13/14 불일치 |
| 재현성 | `seed_dump.sql` 복원 → `smoke.sh` | `smoke.sh` 가 demo seed 의 chunk id 를 하드코딩해 클론 경로에서 2건 실패 |
| 왕복 무결성 | 덤프 생성 후 md5 대조 | psql 출력을 줄 단위로 파싱해 값이 깨지던 문제 |
| 화면 노출 문자열 | DB 실측으로 표본 확인 | 매핑 근거 344건 중 112건에 마크다운 잔재 (화면 노출분 42건) |

마지막 항목은 `seed_dump.sql` 을 **실제로 복원해 보는 리뷰**에서 나왔습니다. diff 만
읽었으면 통과했을 건입니다.

## 3. 검색 품질 평가

> 측정 조건·수치 = A, 해석(3.6) = B — #11 분담 그대로입니다.

### 3.1 정답셋

논문 9편에 대해 큐레이터가 손으로 만든 **단락↔코드 315쌍**(대안 정답 포함 344건)입니다.
`database/eval_set_*.csv` 에 커밋돼 있으며, DB 자동증가 ID 가 아니라
**안정 키**(`arxiv_id, chunk_index, github_url, file_path, symbol_name, start_line`)로
보관합니다 — 깨끗한 DB 에 클론하면 ID 가 달라지기 때문입니다.

### 3.2 측정 조건

- 후보는 **그 논문에 연결된 저장소로 한정** — 서비스(`CodeSearchService.SEARCH_SQL_SCOPED`)와 동일한 SQL
- 단락당 후보 평균 **22개**
- 순위는 **pgvector 코사인 거리**로만 결정. LLM 은 순위에 관여하지 않음
- 한 단락에 대안 정답이 여러 개면 그중 가장 높은 순위를 인정(`--multi-gold`)

### 3.3 결과

| 지표 | 값 | 무작위 선택 시 | 배수 |
|---|---|---|---|
| Top-1 | 29.8% (94/315) | 5.3% | **5.6×** |
| Top-3 | 53.3% (168/315) | 16.0% | **3.3×** |
| **Top-5** | **65.4% (206/315)** | 26.7% | **2.5×** |
| MRR@10 | 0.454 | — | — |

**Top-5 가 제품과 맞는 지표입니다** — 화면이 후보 5개를 함께 보여주고 사용자가 그중에서
고릅니다. 파일 경로·줄 번호·원본 GitHub 링크를 함께 제시하므로 5개 중 고르는 비용이
저장소를 직접 뒤지는 것보다 훨씬 낮습니다.

**MRR 은 컷을 함께 적어야 합니다.** 순위를 어디서 자르느냐로 값이 달라집니다 —
같은 정답셋에서 `--k 5` 는 0.428, `--k 10` 은 0.454, 자르지 않으면 0.464 입니다.
Top-1/3/5 는 컷과 무관합니다.

**무작위 하한은 단락별 실제 후보 수로 계산**했습니다. 전체 코퍼스 크기(183)로 계산하면
배수가 열 배 가까이 부풀려집니다.

```bash
python3 scripts/note2ingest/eval_set_tool.py resolve database/eval_set_attention.csv /tmp/ids.csv
python3 scripts/eval_retrieval.py /tmp/ids.csv --k 10 --multi-gold
```

### 3.5 정답셋을 읽을 때의 한계

**정답셋은 큐레이터 판단이지 구현 가능성의 정답이 아닙니다.** "매핑하지 않음"에는
"구현이 존재하지 않음"과 "노트에 대응 코드가 없었음"이 섞여 있습니다. 이 구분은
자동 분류 실험(확장기능 §5.1)에서 실제로 문제가 됐고, 그 절에 사유를 적었습니다.

### 3.6 해석 — "개선"이 아니라 "교정"입니다 (B)

범위 제한 전후로 지표가 크게 움직였습니다(Top-5 41.0% → 65.4%). 이것을 검색 품질
**개선으로 읽으면 안 됩니다.** 정답셋은 정의상 정답이 그 논문 저장소 안에 있으므로,
후보를 그 저장소로 좁히면 **정답이 아닌 후보만 사라집니다.** 순위를 매기는 함수는 한
글자도 바뀌지 않았습니다 — 같은 랭킹을 올바른 후보 집합 위에서 다시 잰 것입니다.

같은 이유로 "랜덤 대비 배수"는 반대로 내려갑니다(15.0× → 2.5×) — 후보 풀이 183 에서
논문당 평균 22 로 줄어 무작위 적중률이 올라가기 때문입니다. 배수는 단락별 실제 후보
수로 계산했으며, 전체 코퍼스 크기로 나누면 10배 가까이 부풀려집니다(평가 스크립트가
실제로 그렇게 계산하고 있던 것을 교정했습니다 — 52.3× 표기가 교정 직후 5.7× 로,
이후 정답셋 수정(아래 ②)을 거쳐 현재 5.6× — §3.3).

검색 실패는 세 종류로 갈라 각각 다르게 처리했습니다. 셋을 뭉뚱그리면 "한 것"과
"안 한 것"의 경계가 사라집니다.

| 유형 | 처리 | 성격 |
|---|---|---|
| ① 교차 오염 (다른 논문 코드가 후보에 섞임) | **보정 완료** — 범위 제한(#20), Top-1 오답의 47.6% 제거 | 스코프 교정 |
| ② ResNet prototxt 정답 (산문과 안 붙는 설정 파일) | **보정 완료** — concept 단락 19개를 Python 구현 정답으로 재지정, Top-1 11.9→19.0% / Top-5 26.2→45.2% | 정답셋 오류 수정 |
| ③ 동종 심볼 혼동 (같은 저장소 안 유사 심볼) | 랭킹 함수 문제로 남김 — [#18](https://github.com/Ae-Ti/CodeAtlas/issues/18) | **랭킹 미개선 — §9 Limitations** |

①은 스코프 교정, ②는 정답셋 오류 수정 — **둘 다 랭킹 개선이 아닙니다.** 랭킹 자체는
아직 개선하지 않았고(하이브리드 검색 후보는 #18), 이 구분이 이 절 수치를 읽는
기준입니다. 지표가 좋아 보이게 만드는 방법과 제품이 좋아지는 방법은 다릅니다.

## 4. 시스템 아키텍처와 기술 스택

### 4.1 전체 구조

```
① 적재     논문 단락 + 저장소 코드 블록 (수동 큐레이션 §2 / 업로드 파이프라인 §6.3)
             └─▶ PostgreSQL 17 + pgvector — embedding vector(768), nomic-embed-text

② 사전계산  POST /api/admin/curate-pending
             pgvector 코사인 거리로 후보 Top-K → TACC 선별 → qwen3:8b 설명 생성
             └─▶ paper_code_mappings 저장

③ 조회     POST /api/agent/query
             사전계산 있음 → 즉시 반환 (source=precomputed, 실측 0.049초)
             없음        → ②를 그 자리에서 실행 (source=live, 실측 27.3초) 후 저장

④ 표면     React 19 (Monaco 코드 뷰어 · React Flow 그래프 · 챗봇 · 업로드)
           MCP 서버(SSE) — SearchPaperChunk · FindCodeImplementation ·
                           QueryMetadataSQL · CurateContext
```

기술 스택: Spring Boot 4.1 + Spring AI 2.0 / React 19 + Vite / PostgreSQL 17 +
pgvector / Ollama (qwen3:8b · nomic-embed-text) / Python 3 (적재·평가 스크립트,
표준 라이브러리만).

### 4.2 설계 결정과 근거

- **사전계산 / 라이브 이중 경로.** 매 요청마다 로컬 LLM 을 부르면 27초가 걸리고 시연 중
  Ollama 가 멈추면 그대로 장애가 됩니다. 큐레이션된 논문은 미리 계산하고(0.049초),
  신규·ad-hoc 질의만 라이브로 처리하며 결과를 저장해 두 번째부터는 즉시 응답합니다.
- **순위를 정하는 것은 LLM 이 아닙니다.** 후보 순위는 pgvector 코사인 거리로 결정되고
  LLM 은 선별된 1위 후보에 대한 *설명*만 생성합니다 (§5).
- **검색 범위는 논문에 묶입니다.** 후보를 그 논문에 연결된 저장소로 한정합니다 —
  교차 오염(범위 제한 전 Top-1 오답의 47.6%)을 스코프에서 차단합니다 (§3.6 ①).
- **NL2SQL 은 4중 가드.** `SELECT` 시작 검사, 단어 경계 DDL/DML 블록리스트, 세미콜론·
  주석 차단과 100행 상한, read-only 트랜잭션. 노출 테이블도 메타데이터 3종뿐이며,
  생성된 SQL 을 화면에 그대로 노출해 검증 가능성을 유지합니다.
- **TACC (Task-Aware Context Curation).** 후보 중복 제거 → 유사도 상위 선별 → 선별
  근거를 자연어로 요약. 선별 수치(후보 N → 제외 M → 선택 5)를 화면에 표시합니다.
- **포트 인터페이스.** 검색·매핑·큐레이션이 `CodeAtlasPorts` 인터페이스 뒤에 있어
  A(검색 엔진)와 B(에이전트·화면)가 mock 기준으로 병렬 개발했고, 다른 문서 도메인으로의
  이식 접합면이기도 합니다.
- **MCP 서버.** 위 도구 4종을 SSE 로 노출합니다 — CodeAtlas 는 종점이 아니라 다른
  에이전트가 부를 수 있는 도구입니다.

## 5. AI 모델 활용 방식

**오픈웨이트 모델 로컬 구동이며, 런타임에 상용 AI API 를 호출하는 경로가 없습니다**
(운영규정 제9조 대응 — 상세는 `docs/AI_모델_활용_명세.md`).

| 모델 | 라이선스 | 용도 |
|---|---|---|
| `qwen3:8b` (Ollama) | Apache-2.0 | 매핑 설명 생성 · NL2SQL · 챗봇 · AI 답변 · 업로드 단락 분리 |
| `nomic-embed-text` (Ollama) | Apache-2.0 | 단락·코드 블록 임베딩 (768차원) |

- **순위 결정은 LLM 이 아니라 pgvector 코사인 거리입니다** (제9조②1다). LLM 산출물은
  설명·요약·경계 제안뿐이며 검색 순위에 관여하지 않습니다.
- **LLM 은 비결정적이지만 재현성은 구조가 보장합니다** (제10조①) — 설명은
  `seed_dump.sql` 에 결과물로 커밋되어, 심사자가 복원하면 우리가 본 것과 같은
  문자열을 봅니다.
- 생성 모델은 `CODEATLAS_LLM` 환경변수로 교체 가능합니다(기본 qwen3:8b, Ollama
  오픈웨이트만). 임베딩 모델은 저장된 벡터 공간과 묶여 있어 교체 대상이 아닙니다.
- 챗봇·AI 답변의 환각 방지: 프롬프트에 근거 제한을 걸고, **가리킬 대상이 없는 인용
  표시는 렌더러가 결정적으로 제거**합니다(확률적 지시가 아니라 구조적 보장 — §9).

### 6.1 화면 7종

| 화면 | 하는 일 | 핵심 실측 |
|---|---|---|
| Dashboard | 카탈로그 현황 · 논문별 대표 매핑 | 라이브 집계 |

| AI Agent | 자연어 질의 → 단락 검색 → 매핑·TACC 근거, **질문에 대한 AI 답변**(opt-in) | AI 답변 15.6~19.1초(B 환경, 5회) / 31.2~32.9초(A 환경) |
| NL2SQL | 자연어 → read-only SQL, 생성 SQL 원문 노출 | 7~45초 |
| Graph | 논문별 클러스터 + 논문 필터 칩 | 논문 9편 전부 표시 |
| Chat | 검색 기반(RAG) 챗봇 — 근거 칩 + 스트리밍 | 첫 토큰 **1.6~8.8초** |
| Upload | arXiv ID + GitHub URL → 분리·적재·임베딩·큐레이션 자동 | 논문 1편 36~43분 (§6.3) |

### 6.2 질문에 답하는 경로의 분리

`/api/agent/query` 는 질문을 단락 선택에만 쓰고 응답은 "단락↔코드 매핑 근거"로
고정입니다(사전계산과 정합). 질문 텍스트 자체에 답하는 경로는 별도로 분리했습니다 —
AI 답변 버튼과 챗봇은 매 호출 라이브 생성이며 **DB 에 저장하지 않고**, 60초 하드
타임아웃과 실패 카드로 시연 안정성을 지킵니다. 근거 없는 질문에는 "이 섹션에는 나와
있지 않다"로 답하는 것을 실측으로 확인했습니다.

### 6.3 업로드 파이프라인 — 실사용 2회 완주

확장 전략(확장기능 §5.1)의 1단계 실측(경계 IoU·매핑 판단 혼동행렬)을 거쳐, 이번
제출에 화면까지 구현했습니다.

```
arXiv 메타 → LaTeX 소스 → 저장소 클론 → ast 리프 심볼 추출
  → qwen3 단락 분리(경계만 제안, 원문은 코드가 슬라이스) → 적재 → 임베딩 → 큐레이션
```

| 실측 | 단락 | 코드 블록 | 매핑 | 시간 |
|---|---:|---:|---:|---|
| U-Net + milesial/Pytorch-UNet | 11 | 30 | 55 | 35.6분 |
| GAT + PetarV-/GAT | 21 | 28 | 105 | 43.4분 |

두 건 모두 **파이프라인 실증 실행이며 카탈로그에 남기지 않았습니다**(`seed_dump`
복원). `milesial/Pytorch-UNet` 은 GPL-3.0 이라 §7.3 기준으로 카탈로그 대상이
아니며, 그래서 실증 후 제거했습니다 — 라이선스 규정이 문서로만 있는 것이 아니라
실제로 집행됨을 보여주는 사례이기도 합니다.

두 실행 모두 특정 섹션의 LLM 타임아웃 → 문단 단위 폴백을 겪고도 완주했습니다 —
폴백이 품질 손실이 아님은 §5.1 IoU 재측정(문단 분할 0.822 > LLM 병합 0.701)이
보증하며, 같은 근거로 업로드 경로의 호출 타임아웃을 150초로 분리했습니다.
현재 지원 범위는 arXiv LaTeX 소스 논문 + Python 저장소이며, 그 밖은 검증을 거치는
ingest JSON 업로드 경로를 씁니다.

```bash
./scripts/doctor.sh && ./scripts/smoke.sh     # 환경 점검 + 전체 API 8종 호출
cd backend && ./mvnw test                     # DB·Ollama 없이 46건 전부 통과
```

## 7. 라이선스 및 컴플라이언스

### 7.1 왜 대응이 필요한가

`database/ingest/*_ingest.json` 에 **저장소 코드 원문이 들어간 채 공개 저장소에 커밋**되고
화면에도 표시됩니다. 이는 각 저장소 라이선스가 말하는 **재배포**에 해당합니다.

- 인용 코드는 **수정하지 않았습니다.** 각 블록은 지정 커밋의 해당 줄 범위와 바이트 단위로 일치합니다
- 출처(저장소·커밋·파일·줄 번호)는 `code_blocks` 와 `database/seed_manifest.csv` 에 있습니다
- 라이선스 전문은 `database/licenses/` 에 원본 그대로 두었습니다
- 고지는 `database/THIRD_PARTY_LICENSES.md` 와 루트 `NOTICE` 입니다

`NOASSERTION` 입니다. **LICENSE 원문을 읽고 판단**했습니다.

## 8. 팀 구성 · 역할 분담 · 기여도

본 프로젝트는 2인 팀의 제한된 개발 기간을 고려하여 AI 기능을 **Retrieval AI**와
**Agent AI**로 분리하여 개발하였습니다. 팀원 A는 논문 및 코드 데이터를 수집·분할·
임베딩하고 PostgreSQL pgvector 기반 유사도 검색 엔진을 구현하였습니다. 팀원 B는 검색
결과를 활용하는 MCP 기반 도구 호출 구조, NL2SQL, TACC 기반 context 선별 로직, React
기반 시각화 대시보드와 업로드·챗봇 기능을 구현하였습니다. 이를 통해 한 명에게 AI
기능이 집중되지 않도록 역할을 분산하였으며, API 명세(`docs/api-spec.md`)와 mock
JSON 을 기준으로 병렬 개발을 진행하였습니다. (상세 RACI: `docs/CodeAtlas_팀_역할분담.md`)

협업은 **상호 반증 리뷰**로 진행했습니다 — 서로의 주장·수치를 상대가 재현 실험으로
검증한 뒤 머지했고, 그 왕복 기록이 `docs/2026-08-*.md` 작업 정리 6편에 남아 있습니다.
대표 사례: "실행 간 변동"으로 이름 붙었던 현상이 반복 실험(A)과 산출물 추적(B)으로
"타임아웃 폴백"과 "환경 간 판정 불일치"로 갈라진 것(§5.1), 검색 임계값 제안이 20문항
분포 실측으로 반증되어 렌더러 결정층으로 재설계된 것(#55).

개인별 기여도는 `.mailmap` 적용 **로컬 `git shortlog -sne`** 기준으로 첨부합니다 —
GitHub 기여 그래프는 `.mailmap` 을 읽지 않아 초기 커밋 8건이 미귀속으로 표시되므로
로컬 shortlog 임을 명시합니다.
