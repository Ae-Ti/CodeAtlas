## 2. 합동 테스트 피드백 5건이 만든 작업 흐름

8.23 합동 웹 테스트에서 나온 5건을 분류부터 했다 — 버그 1 · UX 2 · 설계 범위 2.

| # | 피드백 | 판정 | 처리 |
|---|---|---|---|
| ① | 자연어에 자유롭게 답하는 AI 필요 | 설계 범위 | #52(질문 답변 버튼) + #54(챗봇)로 구현 |
| ② | 검색 결과에서 코드를 못 봄 | 기능 누락 | #51 — PaperDetail 의 Monaco 를 컴포넌트로 추출해 Agent 재사용 |
| ③ | NL2SQL 작동 안 하는 듯 | UX | 실측 7~45초 — 로딩 안내 문구(#51) |
| ④ | 그래프에 논문 9편 중 4편만 | 데이터 선별 결함 | 전체 유사도순 → 논문별 top-N(#51), 이후 클러스터 배치(#58) |
| ⑤ | 업로드 페이지 없음 | 설계 범위 | #54 로 구현 (아래 §3) |

곁가지로 잡힌 것: A 환경(:5174)에서 질의만 403 — **CORS 허용 오리진이 5173 정확
일치**여서 POST 만 막히던 것(#53). 브라우저가 same-origin 이어도 **POST 에는 Origin 을
붙이고 GET 에는 안 붙여서**, GET 화면은 멀쩡한 채 POST 만 막혔다 — 가르는 건 출처가
아니라 메서드다(A 정정, WebCorsConfigTest 주석과 동일). Agent 의 실질 한계도 이때
확정 — `/api/agent/query` 는 질문을 chunk 선택에만 쓰고 라이브 경로도 `curateContext(…, chunkText, …)` 라 **질문 텍스트가 생성에
전혀 들어가지 않는다**. 같은 chunk 에 걸린 두 질문이 같은 설명을 받는 간극을
#52 가 채웠다(사전계산 경로와 완전 분리, DB 쓰기 없음, 60초 하드 타임아웃 + 실패
카드, 실측 15.6~19.1초 / 콜드 36.1초 / A 환경 31.2~32.9초).

## 3. 업로드 파이프라인 — 실사용 2회 완주

`arXiv ID + GitHub URL` → 메타 → LaTeX 소스 → 클론 → ast 리프 심볼 추출 →
qwen3 단락 분리 → 적재 → 임베딩 → 큐레이션을 **한 작업**으로(#54). 기존 도구
(latex2chunks·ingest.py)를 서브프로세스로 재사용하고, 백엔드는 단계 파싱과
임베딩·큐레이션만 잇는다.

| 실측 | chunk | code block | 매핑 | 시간 |
|---|---|---|---|---|
| U-Net (1505.04597 + milesial/Pytorch-UNet) | 11 | 30 | 55 | 35.6분 |
| GAT (1710.10903 + PetarV-/GAT, B 직접 실행) | 21 | 28 | 105 | 43.4분 |

두 실행 모두 **한 섹션이 LLM 타임아웃 3연속(480초×3)** 을 먹고 문단=chunk 폴백으로
떨어졌지만 파이프라인은 완주했다 — §5.1 에서 규명한 "타임아웃 → 폴백"의 재현.
여기서 두 개선이 나왔다: 한 문단 섹션은 LLM 생략(`--single-para-no-llm`), 업로드
경로 타임아웃 150초 분리(#57). 후자의 근거는 §5.1 IoU 재측정 — **문단 분할 0.822 >
LLM 병합 0.701, 폴백이 품질 손실이 아니므로 24분을 기다릴 이유가 없다**(→ 최악 8분).

A 리뷰로 붙은 안전장치: 파이썬 단계 60분 watchdog + 취소 API, curate-pending 과
겹치면 실패 대신 대기, 매핑 수를 업로드 논문 기준으로 재계산, arxivId 정규식 검증,
작업 디렉터리 정리. **시연 규율은 대본 점검 0번으로**: seed_dump 복원 후 촬영 끝까지
업로드 금지 — 수치(315쌍·65.4%)가 전부 9편 기준이라서다. 테스트 데이터는 확인 후
복원 완료(현재 9편/376/2,011 기준선).

## 4. 챗봇 근거 왕복 — 임계값은 실패하고 렌더러가 남았다

챗봇(#54)은 질문마다 단락 top4 + 사전계산 1위 코드를 근거로 스트리밍 답변한다
(think 끔 — 첫 토큰 19~23초 → **1.6~8.8초**). B 가 발견한 문제: 서비스 사용법
질문("새 논문은 어떻게 추가해?")에 무관한 ViT 단락이 근거로 붙고 본문에 [1]이
달렸다. 왕복 두 번으로 결론이 뒤집혔다:

| 라운드 | 시도 | 반증·확정 |
|---|---|---|
| ① B: 근거 하한 0.60→0.65 + 프롬프트 인용 규칙 | A 가 **두 겹으로 반증** — 먼저 **0.65 에서도 원래 버그가 그대로 재현**("업로드는 얼마나 걸려?" ViT 0.660 · "그래프 화면은 뭘 보여줘?" 0.677 이 하한을 넘어 본문 [1] + 칩 표시): 효과가 없었다. 그리고 20문항 실측에서 서비스 질문 최고 0.677 / 논문 질문 최저 0.605 로 분포가 겹쳐 어떤 컷도 양쪽에서 틀리고, BERT·CLIP 질문이 근거를 통째로 잃음: 비용만 있었다. "점수는 논문 단락과 닮았는가를 재지, 논문에 대한 질문인가를 재지 않는다" |
| ② 하한 원복 + **댕글링 [n]을 렌더러에서 결정적으로 제거** | 프롬프트 지시는 모델이 어긴다(근거 0건이던 4회 중 3회, 전체 8회 관찰). 가리킬 대상 없는 인용(날조에 가까움)은 화면에서 0 보장, 실재하는 약한 근거는 숨기지 않음 — 남는 잔여는 PR 에 명기하고 대본 실패 대응 멘트로 방어(#59) |

교훈은 §6 에. 시연용으로는 시나리오 4-1 을 근거·인용이 붙는 논문 질문으로
교체했다(서비스 소개형 질문은 top 0.574 로 근거 0건 — 화면이 밋밋).

그래프는 두 단계로: top-60 이 4편에 쏠리던 것을 논문별 top-N 으로(#51), 2열
배치의 엣지 교차를 **논문별 클러스터(허브+오른쪽 부채꼴)** 로 구조적으로 제거(#58 —
방사 엣지는 교차가 불가능함을 A 가 좌표 계산으로 확인). 남은 밀도 문제(50노드)는
**논문 필터 칩**으로 — 전체 뷰는 지도, 칩 클릭은 그 클러스터만(4~6노드, 대부분 6)
fitView. 유사도 라벨은 포커스에서만.

## 7. 기록해둘 판단 근거

- **모델에게 부탁하지 말고 렌더러에 못 박는다.** 프롬프트 지시(인용 금지)는 근거
  0건이던 4회 중 3회 무시됐지만, 렌더러의 결정적 필터는 **범위 밖 [n] 이 통과할 구조
  자체가 없다** — 강점은 확률이 낮다는 게 아니라 어길 수 있는 구조가 아니라는 것.
  확률적 층과 결정적 층을 구분하고 보장이 필요한 것은 결정적 층에 둔다.
- **두 문항으로 맞은 임계값은 스무 문항에서 무너진다.** 0.615/0.68 은 시험한 두
  질문에선 갈랐지만 분포(0.605~0.677 겹침)는 못 가른다 — 컷을 정하기 전에 분포를
  잰다. 그리고 그 점수가 **무엇을 재는지**(유사도 ≠ 질문 의도)를 먼저 묻는다.
- **폴백이 손실이 아님을 측정해 뒀다면, 기다림의 근거도 사라진다.** IoU 0.822 > 0.701
  측정이 있었기에 타임아웃 480→150초를 근거 있는 결정으로 내릴 수 있었다 — 측정은
  그 순간만이 아니라 다음 결정의 재료다.
- **남은 한계는 PR 에 적고 대응 멘트를 대본에 넣는다.** 챗봇 잔여 한계를 숨기지 않고
  실패 대응 표에 준비된 답으로 옮기니, 한계가 검증의 증거로 읽힌다 (A 제안).
- **수치를 대본에 하드코딩하지 않는다.** 카탈로그가 살아 움직이는 순간(업로드)부터
  대본 속 숫자는 화면과 어긋난다 — chunk id 를 안 적는 것과 같은 규칙을 통계에도.
- **교차 검증이 머지 순서를 구한다.** 같은 파일을 건드리는 PR 들(#55·#56, #52·#54)을
  로컬에서 미리 합쳐 보는 것으로 충돌·회귀를 머지 전에 소진했다.
