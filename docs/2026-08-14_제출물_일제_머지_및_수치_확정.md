## 9. 기록해둘 판단 근거

- **문서에 적힌 수치는 측정 스크립트 버전과 함께 봐야 합니다.** 65.1% 는 #24 교정
  이전 값이었고, 하루 차이로 어긋났습니다. 수치를 확정할 때는 **두 독립 환경 재현**을
  기준으로 삼았습니다 — 이 조건이 심사에서도 가장 강한 방어입니다.
- **리뷰는 diff 가 아니라 실행으로.** #26 을 복원해본 것이 데모를 망칠 데이터 버그를
  찾았습니다. 데이터 PR 은 "실제 적재까지"라는 CONTRIBUTING 규칙이 실증된 사례.
- **DB surrogate ID 를 어디에도 하드코딩하지 않습니다.** smoke.sh(chunk 101)가 정답셋
  CSV 에 이어 같은 함정을 밟은 두 번째 사례라, 데모 대본은 처음부터 섹션 제목으로만
  썼습니다.
- **결과를 저장하는 경로는 반드시 scoped.** 라이브 캐싱을 붙일 때 저장 규칙을 배치와
  공유하는 서비스로 추출한 이유 — 같은 판단이 두 곳에서 갈라지면 한쪽이 언젠가
  틀립니다.
- **LLM 자동화는 "원문을 다시 쓰게" 하지 않습니다.** 업로드 파이프라인 설계에서 LLM 은
  경계만 제안하고 원문은 코드가 슬라이스합니다 — 검수 기준(원문 일치율)을 자동화에서도
  유지하는 방법입니다.
- **.mailmap 은 로컬 증빙까지만입니다.** GitHub 그래프는 못 고치므로, 보고서 첨부 시
  출처("로컬 shortlog, .mailmap 적용")를 밝히는 것이 정직하고 방어됩니다.
