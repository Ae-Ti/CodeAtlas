# CodeAtlas 확장 기능 및 발전 방향

> 1차 평가 **오픈소스 프로젝트로의 발전 가능성(6점)**, 2차 평가 **활용성(15점 · 최고 배점)** 대응 근거 문서
> 관련: [기획서](CodeAtlas_기획서.md) §4 · §5 · §7 / [README](../README.md) §1
> 작성: B (Taeil Bae) — 2026-08-12 (수치는 큐레이션 완주 후 최종본)

## 0. 왜 지금 이게 필요한가

발표에서 첫 슬라이드로 쓸 내용이다. **"좋은 아이디어"가 아니라 "지금 비어 있는 자리"** 라는 것이 핵심이다.

### 0.1 논문–코드 생태계는 세 층으로 나뉜다

| 층 | 답하는 질문 | 대표 서비스 | 상태 |
|---|---|---|---|
| ① 발견 | 어떤 논문이 있나 / 뭐가 화제인가 | arXiv, Semantic Scholar, HuggingFace Papers, arXiv Trending | 건재 |
| ② 연결 | 이 논문의 구현 코드는 어디 있나 | **Papers with Code** | **2025.7 종료** |
| ③ 정렬 | 이 논문의 **이 단락**이 코드의 **어느 함수**인가 | — | **비어 있음** |

**②가 사라졌고, ③은 애초에 아무도 채우지 않았다.**

### 0.2 Trending Papers 류와 역할이 다르다

"논문에 코드가 붙어 있는 목록"을 보여주는 서비스는 지금도 여럿 있다. 하지만 그것들은 전부 ②층에서 멈춘다.
저장소 링크를 받은 다음부터는 사용자가 알아서 해야 한다.

```
Trending Papers 류가 주는 것        CodeAtlas 가 주는 것
───────────────────────────         ─────────────────────────────────────
"Attention Is All You Need"         §3.2.2 Multi-Head Attention
  → github.com/.../transformer        → transformer/SubLayers.py:12-27
                                         MultiHeadAttention.__init__
저장소 하나 = 파일 수십 개            단락 하나 = 함수 하나
```

저장소를 열어본 다음이 실제 병목이다. 파일 수십 개 중 어디를 봐야 하는지는 여전히 사람이 찾아야 한다.

### 0.3 왜 이 층만 자동화가 안 됐나

논문 용어와 코드 심볼이 **어휘를 공유하지 않기 때문**이다.

```
논문 :  "we employ h=8 parallel attention layers, or heads"
코드 :  self.n_head = n_head ; self.w_qs = nn.Linear(d_model, n_head * d_k)
```

`grep "parallel attention layers"` 는 아무것도 못 찾는다. 문자열 검색으로는 원리적으로 닿지 않는 문제라,
임베딩 기반 의미 검색이 실용화된 뒤에야 시도할 수 있는 층이다. 그 조건이 지금 갖춰졌다.

### 0.4 한 줄 정리 (발표용)

> Papers with Code 가 닫히면서 **논문 → 저장소** 연결이 끊겼다.
> CodeAtlas 는 그 자리를 메우는 데 그치지 않고, 아무도 하지 않던 **단락 → 함수** 정렬까지 내려간다.

## 1. 카탈로그 확장 전략 — 후보 추천 + 사람 승인

### 1.1 지금의 한계

현재 카탈로그는 팀원 A 의 **수동 큐레이션**으로 만들어진다. 품질은 이 방식이 만들어낸다 —
논문 9편 / 단락 376개 중 **쪽 번호 100%, 논문 원문 99.2%, 코드 매핑 83.8%** 를 채웠고,
매핑하지 않은 61건도 "저장소에 없는 코드", "실험 결과·Figure", "미구현 기능"으로 분류해
**억지로 채우지 않은 상태**로 남겼다. 자동 수집으로는 이 판단을 못 한다.

문제는 속도가 아니라 **사람 시간에 선형이라는 것**이다. 9편에 나흘이 걸렸다면 90편에는
40일이 걸린다. 논문은 매일 나오는데 큐레이터는 늘지 않는다. 어느 시점에서든 카탈로그는
"우리가 손으로 훑은 것"에 갇힌다.

반대로 전자동 수집은 늘어나지만 틀린다. 그리고 **이 제품에서 오탐 한 건의 비용이 특히 크다** —
"이 단락은 이 함수입니다"라고 단정해 놓고 틀리면, 사용자는 그 답을 검증하느라 저장소를 직접 뒤진다.
그 순간 제품이 존재할 이유가 없어진다.

### 1.2 그래서 중간을 택한다

```
① 후보 소싱 (자동)                    ② 후보 추천 (자동)              ③ 승인 (사람)
────────────────────                  ──────────────────              ─────────────
PWC 아카이브 데이터셋      ──┐
  논문↔저장소 링크           ├──▶  신뢰도 점수 매겨 정렬  ──▶  검토 후 승인/기각  ──▶ ingest.py
  CC-BY-SA-4.0               │        · 저장소 star 수                                    │
                             │        · 논문 제목/초록 ↔ README 유사도                    ▼
GitHub Search API      ──────┘        · 라이선스 유무                              카탈로그 반영
  아카이브에 없는 최신 논문             · 언어(Python) 필터
```

**핵심은 PWC 가 종료됐어도 아카이브 데이터셋은 남아 있다는 점이다.**
서비스는 죽었지만 그동안 축적된 논문↔저장소 링크는 CC-BY-SA-4.0 으로 재사용할 수 있다.
사라진 서비스의 유산을 1차 소스로 쓰고, 아카이브 시점 이후의 논문만 GitHub Search API 로 메운다.

### 1.3 승인 게이트를 남기는 이유

자동화 비율을 100% 로 올리지 않는 것은 역량 부족이 아니라 **선택**이다.

| | 전자동 | 후보추천 + 승인 (채택) |
|---|---|---|
| 확장 속도 | 빠름 | 중간 |
| 정확도 | 낮음 | 유지 |
| 실패 양상 | 조용히 틀린 답을 반환 | 카탈로그에 안 들어감 |

**조용히 틀리는 것보다 안 들어가는 편이 낫다.** 사람이 보는 것은 후보 목록이지 논문 전체가 아니라서,
승인 자체는 건당 수 분이면 끝난다. 병목은 승인이 아니라 소싱이었고, 소싱을 자동화하면 병목이 풀린다.

### 1.4 후보 소싱이 필수라는 것은 측정으로 확인됐다

이 파이프라인이 "있으면 좋은" 게 아니라 **없으면 동작하지 않는다**는 근거가 있다.

검색은 후보를 **그 논문에 연결된 저장소로 한정**한다([§2.3](#23-검색-범위는-논문에-묶여-있다)).
그러니 저장소가 연결되지 않은 논문을 넣으면 검색할 후보 자체가 없다. 범위를 풀어 전체
코퍼스에서 찾게 하면 결과가 나오긴 하지만 **정의상 전부 다른 논문의 코드**다.

실제로 그렇게 동작하던 시절의 측정치가 있다. 후보를 논문으로 묶기 전, 정답셋 315 단락의
**Top-1 오답 중 47.6% 가 다른 논문 저장소**에서 왔다(그 조건의 Top-5 는 41.0%). 논문별로는 ViT 91%, CLIP 74%,
YOLO 71% 였다 — 트랜스포머 계열 구현끼리는 임베딩이 서로를 구분하지 못한다.

**즉 "논문만 던지면 구현을 찾아준다"는 순진한 형태는 성립하지 않는다.**
새 논문을 받으면 반드시 아래 순서를 거쳐야 한다.

```
① 저장소 후보 소싱   PWC 아카이브 → GitHub Search API
② 사람 승인
③ 코드 블록 적재     AST 파싱
④ paper_repositories 연결
⑤ 그때부터 검색이 의미를 가짐
```

§1.2 의 파이프라인은 편의 기능이 아니라 **⑤가 성립하기 위한 전제**다.

### 1.5 목표

| 시점 | 카탈로그 | 방식 |
|---|---|---|
| 8.12 현재 | 논문 **9편** / 저장소 **12곳** / 코드 블록 **183개** | 수동 큐레이션 |
| 3주차 | 후보 추천 스크립트 가동 + 승인 흐름 실증 | 반자동 |

원래 목표(10 → 15~20건)는 수동 큐레이션만으로 이미 근접했다. 그래서 3주차의 목표는
**건수를 더 늘리는 것이 아니라, 늘리는 방법이 실제로 도는 것을 보이는 쪽**으로 잡는다.
건수는 사람 시간을 더 쓰면 늘어나지만, 그건 §1.1 에서 지적한 한계를 그대로 두는 것이다.

현재 적재 현황의 정확한 수치는 [README §10](../README.md#10-데이터-출처와-라이선스) 참고.

## 2. 구조가 확장을 이미 받치고 있다

전략만으로는 "계획"이고, 코드에 자리가 나 있어야 "발전 가능성"이다. 아래 넷은 이미 구현돼 있다.

### 2.1 MCP 서버 — CodeAtlas 는 종점이 아니라 도구다

가장 중요한 항목이다. CodeAtlas 는 자기 화면을 통해서만 쓸 수 있는 웹앱이 아니라,
**MCP 서버로 기능을 그대로 노출**한다. Claude Desktop 같은 MCP 클라이언트를 붙이면
우리 UI 를 한 번도 열지 않고도 논문–코드 정렬 기능을 쓸 수 있다.

```
GET  /sse                              등록 tool 4종
POST /mcp/message?sessionId=...          SearchPaperChunk
                                         FindCodeImplementation
                                         QueryMetadataSQL
                                         CurateContext
```

오픈소스로서의 발전 가능성이 여기서 나온다. 다른 사람이 이 프로젝트를 **가져다 쓰는** 방법이
"포크해서 고친다" 말고 "자기 에이전트에 도구로 붙인다"가 된다.

### 2.2 포트 인터페이스 — 도메인 이식의 접합면

`backend/.../mcp/port/CodeAtlasPorts.java` 가 검색 구현과 도구 계층을 갈라놓는다.

```java
public interface PaperChunkSearchPort  { List<ChunkResult>   search(String queryText, Long paperId, int topK); ... }
public interface CodeSearchPort        { List<CodeCandidate> findImplementations(Long chunkId, int topK); }
public interface MetadataSqlPort       { NlSqlResult         runReadOnlyQuery(String naturalLanguageQuery); }
public interface MappingReadPort       { List<PrecomputedMapping> findMappings(Long chunkId, int topK); }
```

"문서를 단락으로 쪼개 임베딩하고, 코드를 심볼로 쪼개 임베딩하고, 둘을 잇는다"는 구조는
논문에만 성립하지 않는다. 구현체만 갈아끼우면 그대로 옮겨간다.

| 옮겨갈 곳 | 문서 쪽 | 코드 쪽 |
|---|---|---|
| 사내 개발 | 기술 설계 문서 · 위키 | 사내 모노레포 |
| 표준 · 프로토콜 | RFC 793 (TCP) | 커널 TCP 구현 |
| 교육 | 교과서 · 강의 자료 | 실습 예제 저장소 |
| 오픈소스 온보딩 | 프로젝트 아키텍처 문서 | 해당 저장소 |

바꿔야 하는 것은 **① 문서 파서 ② 코드 파서** 둘뿐이고, MCP tool · TACC · NL2SQL · 화면은 그대로다.

### 2.3 검색 범위는 논문에 묶여 있다

`CodeSearchService` 는 후보를 `paper_repositories` 조인으로 **그 단락이 속한 논문의 저장소**에
한정한다. 확장 관점에서 이게 중요한 이유는 두 가지다.

1. **새 논문을 넣으려면 저장소 연결이 선행돼야 한다** — §1.4 에서 본 그대로다.
   `paper_repositories` 가 비어 있으면 그 논문은 검색 대상이 없다.
2. **논문을 늘려도 서로를 오염시키지 않는다** — 카탈로그가 9편에서 90편이 되어도 각 논문의
   후보 풀은 자기 저장소 크기로 유지된다. 전체 코퍼스에서 찾는 구조였다면 논문이 늘수록
   교차 오염이 심해져 확장 자체가 품질을 깎았을 것이다.

저장소가 연결되지 않은 논문은 전체 코퍼스로 폴백하되 응답에 `paperScoped=false` 를 실어
화면이 "다른 논문의 구현입니다"라고 밝힌다. 사전계산 배치는 그 경우 아예 저장하지 않는다 —
잘못된 매핑이 영구히 남기 때문이다.

### 2.4 사전계산 / 라이브 이중 경로 — ad-hoc 확장의 자리

```
POST /api/agent/query
  1) paper_code_mappings 조회 → 있으면 즉시 반환      precomputed   0.049초
  2) 없으면 FindCodeImplementation → CurateContext     live          27.3초
```

2번 경로가 곧 **"카탈로그에 없는 것을 그 자리에서 처리하는" 경로**다.
지금은 큐레이션 누락분 폴백으로 쓰이지만, ad-hoc 저장소 검색을 붙일 때 새로 만들 것이 아니라
이미 도는 경로에 소스를 하나 더 다는 문제가 된다.

### 2.5 모델 교체 가능 — 특정 벤더에 묶여 있지 않다

생성·임베딩 모두 Ollama 로컬 구동이라 런타임에 상용 API 를 부르는 경로가 없다.
임베딩 모델은 벡터 차원(`vector(768)`)만 맞추면 교체할 수 있고, 생성 모델은 제약이 더 낮다.
자세한 내용은 [AI_모델_활용_명세.md](AI_모델_활용_명세.md).

> 순위를 정하는 것은 LLM 이 아니라 pgvector 코사인 거리다.
> 모델을 바꿔도 검색 품질의 뼈대가 흔들리지 않는 이유이며,
> 운영규정 제9조②1다(상용 API 단순 연결 제한) 대응 근거이기도 하다.

## 3. 커뮤니티 기여 지점

외부 기여자가 들어올 수 있는 자리를 명시한다. 2차 평가 **커뮤니티 확장 가능성(10점)** 대응.

| 난이도 | 기여 내용 | 필요 역량 |
|---|---|---|
| 낮음 | **논문·저장소 추가 제안** — 이슈 템플릿으로 접수 | 도메인 지식만 |
| 낮음 | 잘못된 매핑 신고 | 사용 경험 |
| 중간 | 정답셋 확장 (현재 논문 9편 · 325쌍) | 논문 + 코드 독해 |
| 중간 | 다른 언어 코드 파서 추가 (현재 Python AST) | 해당 언어 AST |
| 높음 | 다른 문서 도메인 어댑터 (§2.2) | 전체 구조 이해 |

**"논문·저장소 추가 제안"이 이 프로젝트에서 가장 장벽이 낮은 기여 경로**이며,
그것이 곧 §1 의 카탈로그 확장과 같은 일이다. 외부 기여가 제품 개선에 직결되는 구조다.

기여 절차는 `CONTRIBUTING.md` 에 정리한다 ([#13](https://github.com/Ae-Ti/CodeAtlas/issues/13)).

## 4. Limitations — 하지 못하는 것

발표와 결과보고서에 그대로 옮긴다. 과장하지 않는 편이 방어에 유리하다.

| 한계 | 내용 | 대응 |
|---|---|---|
| 카탈로그 밖 논문 | 아무 arXiv 논문이나 넣으면 되지 않는다. 저장소를 연결해야 검색이 성립한다(§1.4) | §1 확장 전략으로 완화. 완전 해결은 Future Work |
| 언어 | 코드 파싱이 Python AST 기반 | 다른 언어 파서는 커뮤니티 기여 지점(§3) |
| **랭킹 품질** | **아직 개선하지 않았다.** §2.3 은 후보 범위를 고친 것이지 순위 함수를 고친 게 아니다 | 하이브리드 검색이 그 자리 ([#18](https://github.com/Ae-Ti/CodeAtlas/issues/18)) |
| 검색 정확도 | 논문 범위 안에서 **Top-5 65.1% / Top-1 28.6%** (315쌍, 랜덤 대비 2.6×·5.7×). **사람이 후보 5개 중 고르는 전제** | 화면이 근거(파일·줄 번호·원문 링크)를 함께 제시해 검증 비용을 낮춤 |
| 동종 심볼 혼동 | 생성자(`__init__`)끼리, `BasicBlock.forward`↔`Bottleneck.forward` 처럼 같은 저장소 안 유사 심볼끼리 구분이 잘 안 됨 | 측정으로 확인·기록됨 ([#18](https://github.com/Ae-Ti/CodeAtlas/issues/18)) |
| 산문과 안 붙는 코드 | 설정 파일류(Caffe `prototxt`, `.cfg`)는 심볼 이름과 숫자뿐이라 논문 문장과 임베딩이 붙지 않는다. ResNet 정답 21쌍에서 Top-1 4.8% | 해당 논문은 Python 구현을 Top-1 정답으로 두고 설정 파일은 대안 정답으로 유지 |
| 승인 병목 | 카탈로그 확장에 사람 손이 남음 | §1.3 의 **의도된 트레이드오프** |

### 4.1 수치를 읽을 때 — "개선"이 아니라 "교정"이다

§2.3 의 범위 제한 전후로 지표가 크게 움직였다(Top-5 41.0% → 65.1%). 이것을 **검색 품질
개선으로 읽으면 안 된다.**

정답셋은 정의상 정답이 그 논문 저장소 안에 있다. 그러니 후보를 그 저장소로 좁히면
**정답이 아닌 후보만 사라진다.** 순위를 매기는 함수는 한 글자도 바뀌지 않았다.
같은 랭킹을 올바른 후보 집합 위에서 다시 잰 것이 전부다.

동시에 "랜덤 대비 배수"는 반대로 내려간다(Top-5 15.0배 → 2.6배). 후보 풀이 183 에서
논문당 평균 22 로 줄어 무작위 적중률이 올라가기 때문이다.

배수를 잴 때는 **단락별 실제 후보 수**로 랜덤 하한을 계산해야 한다. 전체 코퍼스 크기로
나누면 범위 제한 조건에서 배수가 10배 가까이 부풀려진다 — 실제로 평가 스크립트가 그렇게
계산하고 있었고(52.3배로 표시), 교정 후 5.7배가 됐다. **이전의 높은 배수가 부풀려진
조건에서 나온 값이었다**는 뜻이지 성능이 나빠진 것이 아니다.

결과보고서에는 두 수치를 조건과 함께 적고, **랭킹 자체의 개선은 아직 하지 않았음**을
명시한다. 지표가 좋아 보이게 만드는 방법과 제품이 좋아지는 방법은 다르다.
