# 적재 데이터 검수 리포트

검수일: 2026-08-08

## 대상 파일

| 파일 | 크기 | 기준 형식 |
|---|---|---|
| `database/ingest/attention_is_all_you_need_ingest.json` | 76 KB | `database/ingest_example.json` + `database/Script-2.sql` |
| `database/eval_set.csv` | 68 B | `database/eval_set_demo.csv` |
| `database/eval_set_attention.csv` | 95 B | `database/eval_set_demo.csv` |

검증 방법: `scripts/ingest.py --dry-run` 실행 + Script-2 제약(enum / VARCHAR 길이 / CHECK / UNIQUE)을 스크립트로 직접 대조.
DB 컨테이너(`codeatlas-postgres`)가 실행 중이 아니어서 **실제 id 대조는 하지 못했습니다.**

## 요약

형식 자체는 통과입니다.

```
✅ 검증 통과 — 논문 1 / chunk 63 / repo 1 / code_block 14 / 수동매핑 14
```

Script-2의 enum(`symbol_type`, `relation_type`, `processing_status`), VARCHAR 길이,
CHECK 제약(`ck_paper_chunks_page`, `ck_code_blocks_lines`, `ck_repositories_star_count`),
`uq_paper_chunks_order`(chunkIndex 0~62 연속·중복 없음) 위반은 하나도 없습니다.
Script-3의 embedding 컬럼을 JSON에 넣지 않은 것도 의도대로입니다(backfill 대상).

다만 그대로 적재하면 나중에 깨지는 지점이 아래 4건 있습니다.

| # | 문제 | 심각도 | 영향 |
|---|---|---|---|
| 1 | codeBlocks 14개 전부 `startLine`/`endLine`이 null | 높음 | 재적재 시 중복 행 → 수동매핑 저장 실패 |
| 2 | `eval_set_attention.csv` 첫 행 id 오류 | 높음 | 평가 지표가 엉뚱한 청크로 계산됨 |
| 3 | 논문 메타(`abstract`, `authors`)가 비어 있음 | 중간 | 논문 카드/검색 결과에 저자·초록 없음 |
| 4 | 매핑된 청크가 63개 중 9개뿐 | 중간 | 로드맵 2주차 30쌍 목표에 21쌍 부족 |

## 1. codeBlocks의 startLine/endLine이 전부 null (높음)

`Script-2.sql:217-223`의 유니크 제약은 다음과 같습니다.

```sql
CONSTRAINT uq_code_blocks_location
    UNIQUE (repository_id, file_path, symbol_name, start_line)
```

Postgres의 UNIQUE는 NULL을 서로 다른 값으로 취급합니다. `start_line`이 14개 전부 NULL이라
이 제약이 사실상 무력화됩니다. 결과:

- `ingest.py`의 `ON CONFLICT (repository_id, file_path, symbol_name, start_line) DO UPDATE`가
  충돌을 감지하지 못함 → **같은 파일을 두 번 적재하면 code_blocks가 14행 → 28행으로 중복**
- 이어서 `--insert-mappings`가 쓰는 `block_ref()` 서브쿼리는 `IS NOT DISTINCT FROM`으로 조회하므로
  중복 이후에는 2행을 반환 → `more than one row returned by a subquery used as an expression` 에러

첫 적재는 성공하지만 두 번째 실행부터 깨집니다.

추가로 `transformer/Translator.py` 블록 1건은 `symbolName`까지 null이라 자연키가
`(file_path, NULL, NULL)` 하나뿐입니다.

원인은 JSON의 `_unresolved`에 기록돼 있습니다 — 업로드한 마크다운에 GitHub 줄 번호가 없어서
줄 번호를 채우지 못했고, 같은 이유로 자연키가 겹치는 블록 2건은 아예 제외됐습니다.

**조치**: GitHub 원본 파일 기준 실제 `startLine`/`endLine`을 채웁니다.
당장 어렵다면 적재 전 `scripts/reset_db.sh`로 초기화하는 전제를 반드시 지켜야 합니다.

## 2. eval_set_attention.csv 첫 행 id 오류 (높음)

두 CSV 모두 헤더·인코딩은 정상입니다(BOM 없음, LF, 마지막 개행 있음).
`eval_set_demo.csv`의 `#` 주석 헤더는 `eval_retrieval.py`가 무시하므로 없어도 됩니다.

문제는 두 파일의 id 베이스가 다르다는 점입니다.

**`eval_set.csv`** — JSON의 `mappedCode` Top-1과 완전히 일치합니다.
`chunk_id = chunkIndex + 1`, `code_block_id = codeBlocks 배열 순번`.
즉 **DB를 리셋하고 이 논문만 적재한 상태** 기준이며, 9쌍 전부 JSON에서 재계산한 값과 같았습니다.

**`eval_set_attention.csv`** — 같은 9쌍이지만 `chunk_id = 302 + chunkIndex`,
`code_block_id = 507 + 블록순번`입니다. **seed_demo(청크 101~, 블록 501~) 다음에 적재한 상황**을
가정한 값입니다. 그런데 첫 행이 규칙대로면 `302,508`이어야 하는데 `101,508`로 적혀 있습니다.

```csv
chunk_id,code_block_id
101,508      ← 302 이어야 함. 101은 seed_demo.sql의 demo 논문 "Multi-Head Attention" 청크 id
306,509
310,510
...
```

이 상태로 평가를 돌리면 첫 쌍이 다른 논문의 청크를 평가하게 됩니다.

또한 두 파일은 상호 배타적입니다 — 하나는 "빈 DB에 이 논문만", 다른 하나는 "demo seed 뒤에"를
가정하므로 실제 DB 상태에 따라 **둘 중 하나만 유효**합니다. 쓰지 않는 쪽은 지우는 게 안전합니다.

## 3. 논문 메타데이터 누락 (중간)

- `abstract`가 `""` → `ingest.py`의 `lit()`이 빈 문자열을 NULL로 바꾸므로 초록이 비어서 들어갑니다
- `authors`가 `[]` → `'[]'::jsonb`. NOT NULL 위반은 아니지만 저자 표시가 안 됩니다
- `tokenCount`가 63개 청크 전부 없음 → nullable이라 적재 자체는 문제 없음

부수적으로 `symbolName`에 심볼이 아니라 지역변수명이 들어간 건이 여럿입니다
(`q`, `residual`, `trg_mask`, `beam_size`, `position_enc`, `dec_output___self_model_decoder`).
`symbolType`도 14개 중 8개가 `MODULE`입니다. 스키마상 유효하지만 코드 검색 품질에는 불리합니다.

## 4. 매핑 커버리지 부족 (중간)

63개 청크 중 `mappedCode`가 붙은 것은 9개(매핑 14건)뿐입니다.
나머지는 `_unresolved` 80건으로 빠졌고, 사유는 대부분 다음 둘입니다.

- 해당 섹션에 GitHub 파일 경로가 없어서 codeBlocks로 승격 불가
- 줄 번호가 없어 자연키가 중복되는 블록(문제 1과 동일 원인)

로드맵 2주차 정답셋 30쌍 목표 대비 21쌍 부족합니다.

## 권장 조치

1. GitHub 원본 기준 `startLine`/`endLine`을 채운다 (문제 1·4를 동시에 해소)
2. `abstract`, `authors`를 채운다
3. CSV는 손으로 쓰지 말고 적재와 동시에 생성한다 — id 불일치가 원천 차단됩니다

```bash
python3 scripts/ingest.py database/ingest/attention_is_all_you_need_ingest.json \
    --insert-mappings --eval-csv database/eval_set.csv
```

`--eval-csv`는 각 청크의 `mappedCode[0]`을 Top-1 정답으로 잡고 **DB의 실제 id**로 CSV를 만듭니다.
따라서 `mappedCode` 배열의 맨 앞에 가장 정확한 코드를 두어야 합니다.

4. 사용하지 않는 정답셋 CSV는 삭제해 혼선을 없앤다
