## 1. codeBlocks의 startLine/endLine이 전부 null (높음)

`Script-2.sql:217-223`의 유니크 제약은 다음과 같습니다.

```sql
CONSTRAINT uq_code_blocks_location
    UNIQUE (repository_id, file_path, symbol_name, start_line)
```

Postgres의 UNIQUE는 NULL을 서로 다른 값으로 취급합니다. `start_line`이 14개 전부 NULL이라
이 제약이 사실상 무력화됩니다. 결과:

- `ingest.py`의 `ON CONFLICT (repository_id, file_path, symbol_name, start_line) DO UPDATE`가
  충돌을 감지하지 못함 → **같은 파일을 두 번 적재하면 code_blocks가 14행 → 28행으로 중복**
- 이어서 `--insert-mappings`가 쓰는 `block_ref()` 서브쿼리는 `IS NOT DISTINCT FROM`으로 조회하므로
  중복 이후에는 2행을 반환 → `more than one row returned by a subquery used as an expression` 에러

첫 적재는 성공하지만 두 번째 실행부터 깨집니다.

추가로 `transformer/Translator.py` 블록 1건은 `symbolName`까지 null이라 자연키가
`(file_path, NULL, NULL)` 하나뿐입니다.

원인은 JSON의 `_unresolved`에 기록돼 있습니다 — 업로드한 마크다운에 GitHub 줄 번호가 없어서
줄 번호를 채우지 못했고, 같은 이유로 자연키가 겹치는 블록 2건은 아예 제외됐습니다.

**조치**: GitHub 원본 파일 기준 실제 `startLine`/`endLine`을 채웁니다.
당장 어렵다면 적재 전 `scripts/reset_db.sh`로 초기화하는 전제를 반드시 지켜야 합니다.

## 2. ~~eval_set_attention.csv 첫 행 id 오류~~ — 오진, 취소

**`101,508`이 맞습니다.** 회신 §2의 지적이 정확합니다.

원 리포트는 `chunk_id = 302 + chunkIndex`라는 공식을 세우고 첫 행만 예외라 버그로 판단했지만,
`ingest.py`가 논문을 `arxiv_id`로 upsert한다는 점을 빠뜨렸습니다. `seed_demo.sql`을 다시 대조했습니다.

- `seed_demo.sql:17` — 논문 1의 `arxiv_id`가 `1706.03762`, 즉 **같은 논문이 이미 존재**
- `seed_demo.sql:31-42` — 그 논문의 `chunk_index` 0~3이 id **101~104**
- `seed_demo.sql:86-89` — `setval`로 시퀀스가 **301 / 507**로 복원

따라서 재적재하면 `chunk_index 0~3`은 `ON CONFLICT (paper_id, chunk_index)`로 **UPDATE되어
기존 id 101~104를 유지**하고, 충돌한 행도 `nextval()`은 이미 소비하므로 302~305가 버려집니다.
`chunk_index 4`부터 새 행이 306, 310, … 순으로 붙습니다. **9쌍 전부 이 규칙과 일치**합니다.

정리하면 `eval_set_attention.csv`는 손으로 쓴 파일이 아니라 `--eval-csv` 산출물이고,
`101`은 예외가 아니라 upsert의 정상 결과입니다. **고치면 안 됩니다.**

두 CSV 모두 헤더·인코딩은 정상입니다(BOM 없음, LF, 마지막 개행 있음).
`eval_set_demo.csv`의 `#` 주석 헤더는 `eval_retrieval.py`가 무시하므로 없어도 됩니다.

**여전히 유효한 부분** — 두 파일은 상호 배타적입니다.
`eval_set.csv`는 "빈 DB에 이 논문만"(chunk_id = chunkIndex+1), `eval_set_attention.csv`는
"demo seed 뒤에"를 가정하므로 **둘 중 하나만 유효**합니다. 회신 §9.3에 따라
`eval_set.csv`를 삭제하고 `eval_set_attention.csv`를 정본으로 둡니다.

> 단, §6 조치로 `codeBlocks`가 14 → 13개로 바뀌었으므로 `code_block_id`가 이동했습니다.
> `eval_set_attention.csv`는 §6 절차로 **재생성해야 합니다.**

## 5. chunk content가 인용 한 줄 수준 (높음) — 회신 §5 정정

회신 §5가 지적한 항목입니다. **우선순위 최상단이라는 결론은 맞지만 진단은 일부 다릅니다.**
63개 chunk를 전수 측정한 결과입니다.

| 회신 §5의 진단 | 실측 |
|---|---|
| content가 한국어 해설이라 cross-lingual 검색이 된다 | ❌ content는 **43/63이 영어 전용**, 한국어 우세는 2개뿐 |
| subsectionTitle이 63개 전부 `"논문 텍스트"` | △ 56개 — 나머지는 `논문 참고문헌` 4, `논문 대응` 3 |
| 500~800 token 기준에서 벗어남 | ✅ **이게 진짜 원인** — content 중앙값 **69자**(약 20토큰), 최대 268자 |

즉 언어 불일치보다 **길이**가 지배적인 문제였습니다. content 대부분은 논문에서 따온
영어 인용문 한 줄이거나 LaTeX 수식 한 덩어리라, 임베딩에 들어갈 정보량 자체가 없었습니다.

다만 한국어 문제가 없는 것은 아닙니다. `EmbeddingBackfillRunner`는
`section_title + subsection_title + content`를 이어붙여 임베딩하는데
(`EmbeddingBackfillRunner.java:70-73`),

- `sectionTitle`이 **33/63에서 한국어 요약문**이었고
- `subsectionTitle`은 56/63이 `"논문 텍스트"`로 동일해 구분자 역할을 전혀 못 했습니다

**조치 완료** — 63섹션 구조와 mappedCode 9쌍은 그대로 두고:

- `content` = 기존 인용/수식 + **논문 원문 해당 문단**(ar5iv 1706.03762). 63개 중 56개 보강,
  중앙값 69자 → **504자**
- `sectionTitle` = 논문 실제 섹션명(`Abstract`, `3.2.1 Scaled Dot-Product Attention` 등 22종)
- 기존 한국어 제목은 `subsectionTitle`로 이동 (버리지 않음 — 시연 설명용으로 유지)
- 참고문헌 4건·논문 미서술 3건은 대응 문단이 없어 content 유지, 제목만 표기 교정

## 6. codeContent가 저장소 원문과 불일치 (높음) — 신규

원 리포트에도 회신에도 없던 항목입니다. §1의 "줄 번호를 채우자"를 실행하려고
`jadore801120/attention-is-all-you-need-pytorch` 원본 5개 파일을 받아 대조하다 발견했습니다.

**14개 블록 중 13개가 저장소 원문과 일치하지 않습니다.** 업로드 마크다운의 코드가
재포맷된 상태(인자 줄바꿈, 괄호 추가)라 원본 어느 줄과도 매칭되지 않습니다.

```python
# 저장소 원본 (Optim.py:4,7)
class ScheduledOptim():
    def __init__(self, optimizer, lr_mul, d_model, n_warmup_steps):

# 업로드 마크다운 / JSON
class ScheduledOptim:
    def __init__(
        self,
        optimizer,
        ...
```

재포맷은 JSON 생성 과정이 아니라 **업로드한 마크다운 자체**에서 이미 일어나 있었습니다
(마크다운 2034행에서 확인). 즉 JSON은 노트를 충실히 옮긴 것이 맞습니다.

이 상태로는 §1의 줄 번호를 채울 방법이 없습니다 — 어떤 숫자를 넣어도 실제 코드 위치가 아닙니다.

부수적으로 블록 1건은 `filePath`도 틀렸습니다:
`self.attention = ScaledDotProductAttention(...)`은 `Modules.py`가 아니라 `SubLayers.py:24`입니다.

**조치 완료** — `codeContent`를 저장소 원문(`@132907d`)으로 교체하고 실제 줄 번호를 부여했습니다.
13/13 블록이 해당 줄 범위와 바이트 단위로 일치함을 확인했습니다.
`repositories.commitHash`에 참조 커밋을 기록해 줄 번호를 재현 가능하게 했습니다.
