## 2. eval_set_attention.csv 첫 행 — 오진입니다

**결론: `101,508`이 맞습니다. `302,508`로 고치면 오히려 깨집니다.**

### A가 세운 전제

> `chunk_id = 302 + chunkIndex`. 그런데 첫 행이 `101`이므로 오류.

### 실제 동작

`scripts/ingest.py`는 논문을 **`arxiv_id`로 upsert**합니다 (`ON CONFLICT (arxiv_id) DO UPDATE`).
`1706.03762`는 seed_demo에 **이미 논문 1로 존재**하고, 그 논문의 chunk_index 0~3이 id 101~104로 들어 있습니다.

```
 id  | paper_id | chunk_index |                   content
-----+----------+-------------+------------------------------------------
 101 |        1 |           0 | Multi-head attention allows the model to
 102 |        1 |           1 | We call our particular attention Scaled
 103 |        1 |           2 | In addition to attention sub-layers, eac
 104 |        1 |           3 | Since our model contains no recurrence a
```

chunk INSERT는 `ON CONFLICT (paper_id, chunk_index) DO UPDATE`이므로:

- `chunkIndex 0~3` → **충돌 → UPDATE → 기존 id 101~104를 그대로 유지**
- Postgres는 충돌한 행에도 `nextval()`을 이미 소비하므로 **302~305가 버려짐**
- `chunkIndex 4` → 새 행 → **306**
- 이후 `chunkIndex n (n≥4)` → `302 + n`

### 9쌍 전부 대조

JSON에서 `mappedCode`가 붙은 chunkIndex는 `[0, 4, 8, 12, 14, 17, 29, 39, 46]`,
각 Top-1이 가리키는 codeBlocks 배열 index는 `[0, 1, 2, 3, 5, 7, 9, 11, 12]`입니다.

| 0 | **101** (충돌 → 기존 id) | 101 ✅ | 0 | 508 | 508 ✅ |
| 4 | 306 | 306 ✅ | 1 | 509 | 509 ✅ |
| 8 | 310 | 310 ✅ | 2 | 510 | 510 ✅ |
| 12 | 314 | 314 ✅ | 3 | 511 | 511 ✅ |
| 14 | 316 | 316 ✅ | 5 | 513 | 513 ✅ |
| 17 | 319 | 319 ✅ | 7 | 515 | 515 ✅ |
| 29 | 331 | 331 ✅ | 9 | 517 | 517 ✅ |
| 39 | 341 | 341 ✅ | 11 | 519 | 519 ✅ |

**9행 전부 일치합니다.** `eval_set_attention.csv`는 손으로 쓴 파일이 아니라
seed_demo가 적재된 DB에서 `ingest.py --eval-csv`로 생성된 정상 산출물입니다.

따라서 §6 절차를 지키면 이 id들은 매번 동일하게 재현됩니다.

## 3. 논문 메타데이터 누락 — 영향이 리포트보다 큽니다

리포트는 "초록이 비어서 들어간다"로 봤지만, upsert이므로 **있던 값을 지웁니다.**

`ingest.py`의 papers UPSERT는 `ON CONFLICT (arxiv_id) DO UPDATE SET ...`이고,
`abstract`가 `""` → `lit()`이 NULL로 변환, `authors`가 `[]` → `'[]'::jsonb`입니다.
현재 논문 1은 seed_demo에서 저자·초록이 채워진 상태이므로, 지금 적재하면
**정상 표시되던 논문 카드가 저자·초록 없는 상태로 퇴화**합니다.

`GET /api/papers` 응답의 `authors` 필드는 프론트 논문 리스트/상세가 그대로 쓰므로 화면에 바로 드러납니다.

**조치**: 적재 전에 `abstract`, `authors`를 채워야 합니다. 이건 선택이 아니라 회귀 방지입니다.

## 5. (신규) chunk content가 논문 원문이 아니라 한국어 해설입니다

리포트에 없는 항목입니다. **스키마 위반이 아니어서 `--dry-run`으로는 절대 안 잡힙니다.**

`chunkIndex 0`의 실제 내용:

```
sectionTitle    : "RNN과 convolution 없이 attention만 사용하는 구조"
subsectionTitle : "논문 텍스트"
content         : > "The Transformer, based solely on attention mechanisms,
                     dispensing with recurrence and convolutions entirely." >
```

- `sectionTitle`이 논문의 실제 섹션명(`3.2 Attention` 등)이 아니라 **한국어 요약문**입니다
- `content`가 논문 단락이 아니라 **영어 인용 한 줄이 든 마크다운 인용구**입니다
- `subsectionTitle`이 63개 전부 `"논문 텍스트"`인 것으로 보이며, 구분자 역할을 못 합니다

### 왜 문제인가

`EmbeddingBackfillRunner`는 `sectionTitle + content`를 이어붙여 `nomic-embed-text`로 임베딩합니다.
그러면 **한국어 해설 벡터 ↔ 영어/Python 코드 벡터** 간 cross-lingual 유사도 검색이 됩니다.
`nomic-embed-text`는 다국어 정렬이 강한 모델이 아니라서 cosine similarity가 전반적으로 낮고
평평하게 깔릴 가능성이 큽니다. 즉 **Top-1/3 Accuracy가 데이터 품질이 아니라 언어 불일치 때문에 떨어집니다.**

또한 `content` 길이가 인용 한 줄 수준이면 `tokenCount`가 63개 전부 없는 것과 맞물려
1주차 기준인 "500~800 token chunk"에서 크게 벗어납니다.

### 조치 제안

- `content`는 **논문 영어 원문 단락**으로, `sectionTitle`은 **논문의 실제 섹션명**으로
- 한국어 해설은 버리지 말고 `subsectionTitle`이나 별도 필드로 옮기기 (시연 설명용으로 가치가 있습니다)
- 이게 §1~§4보다 Top-1 Accuracy에 더 크게 작용할 가능성이 높습니다. **우선순위 최상단 권장**

## 6. 적재 표준 절차 (B 확정 — 재적재 사고 방지)

§1이 해결되기 전까지 **반드시 초기화 후 적재**합니다. `seed_demo.sql`의 `setval` 덕분에
id가 결정적으로 재현되므로 `eval_set_attention.csv`도 계속 유효합니다.

```bash
# 1. 초기화 (demo 유지 — B 시연이 논문 3편을 씁니다)
./scripts/reset_db.sh --with-demo

# 2. 적재 + 수동매핑 + 정답셋 동시 생성
python3 scripts/ingest.py database/ingest/attention_is_all_you_need_ingest.json \
    --insert-mappings --eval-csv database/eval_set_attention.csv

# 3. 임베딩 backfill (content가 바뀌면 embedding이 NULL로 초기화됩니다)
cd backend && CODEATLAS_EMBEDDING_BACKFILL=true ./mvnw spring-boot:run

# 4. 사전계산 큐레이션 (63 chunk × Qwen3 — 수십 분. 시연 직전에 돌리지 말 것)
curl -X POST localhost:8080/api/admin/curate-pending

# 5. 평가
python3 scripts/eval_retrieval.py database/eval_set_attention.csv
```

> ⚠️ `--eval-csv` 대상은 `eval_set.csv`가 아니라 **`eval_set_attention.csv`** 입니다.
> demo를 유지하는 전제이므로 id 베이스가 301/507입니다.

### demo seed를 지우는 선택지에 대해

`reset_db.sh`(demo 없이) + 적재도 가능하지만 지금은 권하지 않습니다.

- 논문이 Attention 1편만 남아 B의 대시보드·연결 그래프 시연이 빈약해집니다
- 사전계산 매핑 30건이 사라져 재계산 시간이 더 듭니다
- A의 `seed_dump.sql`(논문 10편)이 나오는 시점에 한 번에 전환하는 게 낫습니다

## 9. 이번 라운드 작업 순서와 충돌 방지 규칙

### 9.1 먼저 — `origin/develop`이 `origin/main`보다 뒤처져 있습니다

§8의 결과로 브랜치 관계가 뒤집혔습니다.

```
origin/main    a76f41d  ← 최신 (데이터 3커밋 포함)
origin/develop f37c8f7  ← 5커밋 뒤처짐
```

이대로 `develop`에서 브랜치를 따면 방금 올린 데이터가 없는 상태에서 시작합니다.
B가 로컬 `develop`(이미 fast-forward로 받아둠)을 push해서 먼저 맞추겠습니다.

### 9.2 각자 올릴 브랜치

| | 브랜치 | 내용 | PR 대상 |
|---|---|---|---|
| **A** | `data/attention-ingest-json` (기존 재사용) | ingest JSON 수정(§5 원문 content, §1 startLine, §3 abstract/authors, §4 매핑 30쌍) + 재생성한 `eval_set_attention.csv` + `eval_set.csv` 삭제 | **`develop`** |
| **B** | `develop` 직접 | 검수 리포트 + 본 회신 문서 (문서라 PR 생략) | — |
| **B** | `feature/ingest-tooling` (신규) | `ingest.py` startLine null 경고 | `develop` |
| **B** | `feature/frontend-dashboard` (기존) | 실제 API 연결본 | `develop` |

`main`은 이번 라운드에서 건드리지 않습니다. 다음 `main` 머지는 시연 직전 안정 버전 확정 때 한 번만.

### 9.3 파일 소유권 고정 (이번 라운드 충돌 위험 구간)

| 파일 | 건드리는 사람 |
|---|---|
| `database/ingest/*.json` | **A만** |
| `database/eval_set*.csv` | **A만** |
| `scripts/ingest.py` | **B만** |
| `docs/데이터_검수_리포트*.md` | 각자 자기 문서만 |

특히 **eval CSV는 B가 커밋하지 않습니다.** `--eval-csv`는 DB를 실제로 돌려야 나오는 산출물이라
양쪽이 각자 생성하면 매번 충돌합니다. **A가 §6 절차를 로컬에서 돌려 나온 결과물만** 커밋합니다.

`eval_set.csv` 삭제도 B가 따로 하지 않고 **A의 PR에 포함**시킵니다 (같은 이유).

> 위 소유권 규칙은 `docs/CodeAtlas_팀_역할분담.md`의 "코드 소유권 경계"에 없던 항목입니다.
> 그 문서는 **공동 관리**이므로 B가 임의로 고치지 않았습니다.
> A가 동의하면 그때 역할분담 문서에 정식 반영하겠습니다.

### 9.4 순서

1. **B** — `develop` push → `origin/develop`을 `origin/main`과 동기화
2. **B** — 검수 리포트 + 회신 문서 커밋·push → A에게 전달 (**§2 오진 정정이 가장 급함**)
3. **A** — `develop` 최신 pull → §7 표의 1~5 작업 → PR to `develop`
4. **B** — 병행: 프론트 머지 + `ingest.py` 경고
5. A PR 머지 후 → **B**가 §6 절차 실행 → Top-1/3 Accuracy·MRR 산출

A의 1~3이 끝나기 전에 적재하면 되돌릴 작업만 늘어나므로, 3번이 끝날 때까지 DB는 현 상태로 둡니다.
